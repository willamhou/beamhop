关于顺手、去处，和被打断的思路

让信息过去。人，留在这里。

“这句，应该给那边看看。”
Beamhop 值得接住的，就是这个瞬间。

产品方向推演 · 可交互随笔交互均为模拟，不连接你的应用

你在网页上读到一段话，想到正在 Codex 里推进的工作。接下来，本来只需要把这段话送过去。

但你先离开了网页，找到 Codex，再翻会话，确认项目，粘贴、解释。等回到文章，刚才读到了哪里，又要找一次。

这里有两次寻找：发送前找去处，发送后找回思路。Beamhop 的产品力，应体现在这两次寻找越来越少。

Beamhop 负责把材料送进已有的工作；推理、执行和产出，继续发生在外部 agent 里。

01

你记得那件事，却不记得会话名。

“Codex”只是应用名。真正的去处是：昨天，在 beamhop 项目里，讨论发送后不要抢焦点的那一场。会话一多，几个相似的标题就足以让人犹豫。

人认路，会记住门口那棵树。认一场工作，也需要这样的线索：哪个项目、上次停在哪一句、自己给它留了什么称呼。产品应当把这些线索放到眼前。

下面先只给会话标题。试着找那场“发送后不要抢焦点”的讨论，再切到「带上工作线索」。认出来后，把它设为当前去处。

线索帮助你认出会话；你确认的那个具体接收位置，才决定材料实际送去哪。标题相同，也不能被当作同一个地址。

这些接收位置从哪里来？

这里不假设 Beamhop 能读到所有应用的所有聊天。一个可行的首次连接方式是：你本来就在目标会话里工作时，通过接收端的集成，把“当前会话”登记给 Beamhop，并给它一个好认的称呼。之后从别处发送，才不必重新找它。项目、最近一句等线索，也必须来自接收端允许提供的信息。

这需要目标工具提供可寻址的会话或接收接口。尚未连接的会话不会神奇地出现在列表中；如果做不到稳定寻址，就应明确提供手动交接，不能把“打开了 Codex”写成“送进了正确会话”。

02

找到一次，下一次就该少找一步。

通讯录让我们不用每次重新打听号码。Beamhop 也可以记住一个更小、更具体的关系：这一轮材料，送到刚才确认的那场工作。

于是，选中一段文字之后，按钮直接带着去处。需要改变时，再换一个。熟悉之后，手势或快捷键也能表达“把选中内容送到当前去处”，不用每次从一句 prompt 开始。

“这里”由选区说明，
“那里”由你确认过的去处说明。

这个动作本身已经有意义：补充上下文。若想让对方立刻做什么，可以再补一句。“补充材料”和“要求执行”应该分得清楚。

下面一直是你正在阅读的应用。先送一段，再换到 PDF 送第二段，看看还需不需要重新找会话。也可以先放到右下角，读完再决定。

03

还不知道给谁，就先留在手边。

有时候，人只知道“这个可能有用”。这时逼人选择会话，仍然是在打断。右下角可以像拿在手里的几张纸：先留下原文和出处，等想到去处，再一起交出去。

知道去处时直接送；不知道时才暂存。剪报板的价值是允许片刻犹豫。它不应变成每次发送都要经过的中转站，更不必承担整理所有知识的任务。

工作可以是非线性的。同一段材料可以给负责交互的会话，也可以给负责实现的会话。让它们继续各自的工作，Beamhop 记住材料的去向即可；不用为了每次关联，再长出一个 topic 或 fork。

04

产品力，在那个没有发生的打断里。

对 Beamhop，最值得打磨的一次成功体验很小：用户在一篇长文里看见依据，顺手送给正在工作的 agent，接着读下一句。

可以这样检验：同一个人第二次向同一处发送时，是否真的少找了一遍？发送之后，是否仍然知道自己在读什么？还要看有多少次需要纠正目的地，以及“已送达”是否经得起核对。

AI 可以帮助从已授权的工作线索中找候选、给相似会话补上可辨认的摘要。最终的接收地址需要确定，已确认的去处也不该被一次猜测悄悄换掉。这是信任能积累的前提。

让人花在“送到哪里”的注意力，
回到“为什么这段有用”。

这篇演示的现实边界

所有会话、材料、连接状态和回执都是虚构样例；不会向 Codex 或其他工具发送数据。“接收端已确认”只表示本演示中的交接完成，不代表 agent 已理解、执行或完成工作。

Beamhop 仓库已经包含采集、来源预览、外部投递与恢复路径。当前部分投递方式会激活目标应用，或只填入输入框、仍需用户提交。本页提出的“具体会话可寻址、保持前台不变、可确认送达”，需要接收端支持，不能仅凭 MCP 的存在就视为已经实现。快捷键式直送也应先确保投递可靠，再缩短步骤。
