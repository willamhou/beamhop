Interactive essay 03 · Design exploration

Respond first.
Understand next.

A useful tool should not make you wait at the door while it figures things out.

Select text, a file or an image, and invoke Beamhop. Check the material, say what you want done, and hand it to a specific app and session. When background handoff is supported, send it and continue your own work.

Leave room for the work at hand.

The previous version exposed the source, work description, relation, reference, input and actions at once. Each had a reason to exist, but together they felt like a form. The lesson from Spotlight and Raycast is a density that makes input and action immediately recognizable.

The initial view keeps material, instruction and receiver. Types and counts are visible, files have names, and images have thumbnails; open the collection to inspect more. The instruction field has a distinct background and a clear label. It supports multiple lines and can be left empty when adding context. The app and session stay visible, with the project on a secondary line for recognition.

The actual Mac implementation should keep system panels, text input, menus and standard buttons. Adopt new appearances through system controls and materials, while preserving readability on older systems and with reduced transparency or increased contrast. This web preview cannot replace validation in a real NSPanel.

Make the material easy to check.

Materials can include selected text, additional text, files and images. Edit text directly, then type or paste additional material within the same panel. Edits are retained automatically and used for handoff. The original selection stays in this page for comparison and restoration; provenance remains. Files show their name and type, rather than passing off a path as an attachment. Images have thumbnails and full previews. Remove any item; references only join the handoff when explicitly added.

When a destination supports only text, images and files must not disappear silently. Identify unsupported materials so the user can change destination or remove them. Choose or drop local files, or paste images in this page; the demo neither uploads them nor parses file contents.

Projects help recognition. Apps and sessions receive the material.

One deployment plan might have implementation work in Codex and risk discussion in another app. A destination is therefore a complete connection: work name, receiving app and specific session. Select the whole connection once from a single menu. The panel keeps the confirmed choice without asking you to select a project and then an app each time, or automatically broadcasting to multiple agents.

A registered connection must also describe what it accepts and how handoff works. App names here demonstrate choosing among apps. Capabilities are fictional examples, not claims that those apps support background sending, stable session addresses or attachments. Native integration still requires verification.

After sending, keep reading.

For connections with an explicit address, background delivery and receipt confirmation, the primary action is Send. The panel closes while the source stays active; open the receiver when needed. Where only composer insertion is supported, the action says Continue in the app and explains that the app will open. Clipboard-only connections report only that text was copied; the user must still check the session and paste.

Save to Pocket stores an independent batch of materials, instructions and destination. New captures do not inherit the previous instructions; restoring a batch does not send it. With current input present, the restore action says Save current and restore. Add materials only copies the selected batch into the current draft, preserving its instructions and destination and keeping the original batch in Pocket.

A failed record keeps the material and actual destination from that attempt. Retry does not redirect it to a later choice. This page simulates known unavailability before connection. A real missing receipt is not a confirmed failure: check status or use receiver-supported deduplication before trying delivery again.

Experience comes from records, not a model provider.

“Project B’s deployment experience” should come from records you allow Beamhop to use, with their source, date and conditions preserved. Finding that record does not require a model-generated answer or an API key from the user.

The proposed first version uses a local recommendation process: full-text search for content; client names, project identifiers and document references for relations; then ranking informed by confirmed destinations and recent use. An explicit choice takes precedence. When there is no reliable match, offer recent destinations without inventing a connection.

For example, a client identifier can link an email to A’s deployment plan. A cross-project reference can appear when the plan’s existing “on-premises deployment” entry matches B’s pilot record, or when both cite the same deployment specification. Show this evidence as the reason; no model needs to write an explanation. These are proposed rules. This page uses fixed examples and does not implement a general recommendation engine.

Keep recommendations small and evidence clear.

  1. Retrieve first.Use a local inverted index and full-text search to retrieve candidates. Chinese requires tokenization or character and word fragment matching. Keep exact matches for people, clients, paths and document identifiers.
  2. Follow existing relations one step.Find neighboring records through citations, explicit links and shared sources. Bound that traversal so that being in the same large project does not recommend everything. Deduplicate repeated content.
  3. Rank by evidence.Distinguish a shared client, shared constraint or citation from mere recent use. Start with explainable rules or rank fusion. Use explicit corrections within their relevant scope, rather than turning one choice into a permanent preference.

Ordinary indexes, adjacency lists and a small ranking routine can do this without a generative model or an initial vector model. Fixed classifiers suit stable types such as questions and constraints, but do not by themselves resolve membership in continually changing projects. If real material reveals a meaningful gap in synonyms or implicit connections, then compare dictionaries, semantic indexes and small models by benefit and cost.

Matching terms or citations only establishes a reason to look. Preserve the original conditions when judging applicability. The system must not turn “related” into “proven to work.”

Opening and recommending are separate paths.

The panel shows the selection, prompt and confirmed destination without waiting for retrieval. Update indexes incrementally as work records change, and query existing indexes on invocation. Input and basic handoff remain available during initial indexing and background updates.

Late results may add an entry point, but must not change the destination, rewrite the prompt, take focus or move the buttons. Dismissal invalidates the old request; reopening must not mix in results from a previous selection.

These are requirements for the native implementation, not benchmark results. Measure time from shortcut to editable input separately from time to candidates, covering cold starts, long idle periods, Chinese material, large indexes and different Macs. Avoiding models does not remove the need to test performance.

Apple’s on-device AI: available to consider, not required.

The on-device Foundation Models model supports classification, summarization, entity extraction and short-text judgment. On-device inference can work offline without a cloud API key from the user. The APIs are available starting with macOS 26, but device, region, language, Apple Intelligence settings and model download status affect availability.

Apple also notes that on-device generation can take seconds, and its current support page still lists restrictions for mainland China. Newer framework versions support other model paths, so using Foundation Models does not automatically mean fully offline operation.

This makes it a technology to evaluate, not a requirement for Beamhop. Validate local recommendations without model dependencies first. Natural Language, Create ML and Core ML remain candidates for later use when they solve observed problems. The presence of system AI is not a reason to add a wait.

Make this small action work first.

Acceptance should require no model configuration or network connection to type, find known destinations and prepare locally; retain material when the external tool is unavailable. Delayed recommendations must not interrupt an action in progress. B’s original record and conditions must remain inspectable.

This previews a product direction. Work names in the current native app still primarily bind to applications. Mixed material, independent held batches, exact sessions and background handoff shown here are not integrated with real apps. Support must be verified for each connection. Copied, draft prepared, receipt confirmed and task completed are different states.
